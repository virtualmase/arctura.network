# Arctura Network Growth Operating Plan

Updated: 2026-08-30

## Objective

Increase Arctura's durable value by proving that people use its tools, return to its record, contribute improvements, and trust its published evidence. A third-party domain estimate is a lagging signal, not the operating target.

## Baseline

- Hostinger estimate supplied by the owner: approximately $700.
- GitHub, trailing 14 days: 32 views from 2 unique visitors; 98 clones from 49 unique cloners.
- Repository: 0 stars, 0 forks, 0 watchers, 1 open issue at baseline.
- Website analytics: no verified first-party event instrumentation in the repository.
- Public product surface before this iteration: documentation, evidence, Field Notes, and a local-testnet implementation record.

GitHub traffic is directional. Clone counts do not establish product adoption, active operators, or customers.

## North-star outcome

**Monthly verified work orders completed:** distinct exported work orders followed by an optional, privacy-preserving completion signal in a future iteration.

Until completion measurement exists, use **Work Order builder starts** and **exports** as provisional activation metrics.

## Supporting metrics

1. **Useful-tool activation** — work-order exports / builder visits.
2. **Return use** — visitors who use a tool or evidence route in more than one week of a rolling 28-day window.
3. **Verified contribution** — merged contributions or accepted evidence records per month.

Guardrails:

- No unsupported mainnet, staking, emissions, production, customer, or live-data claim.
- No collection of work-order content without explicit consent.
- All public prototype routes pass tests, canonical checks, and evidence-boundary checks.

## First 90 days

### Days 0–30: one useful product

- Ship the local-only Agent Work Order builder.
- Add privacy-respecting event measurement after selecting an analytics source of truth.
- Publish one worked example and one evaluation template.
- Establish repository description, README, issue templates, and a monthly maintenance review.

### Days 31–60: proof of use

- Interview 5–10 agent builders or operators.
- Publish aggregated, consented lessons from real work orders.
- Add a work-order validator and versioned JSON schema.
- Create a public prototype changelog with tested and proposed states.

### Days 61–90: contribution loop

- Accept example work orders and evaluation cases through reviewed pull requests.
- Publish the first monthly Work / Proof / Stewardship record.
- Add one narrow reference worker that executes a harmless, deterministic work order.
- Compare expected result against recorded checks and publish failures as well as passes.

## Distribution loop

Every release should produce:

1. one working artifact;
2. one dated Field Note explaining the problem and evidence;
3. one concise GitHub release with a reproducible test;
4. one social update linking to the artifact, not a generic homepage;
5. direct outreach to a small set of relevant builders for feedback.

Do not mass-produce search pages. Publish only when the work creates a useful tool, source record, experiment, or lesson.

## Maintenance cadence

- Weekly: route, uptime, broken-link, and claim-boundary checks.
- Monthly: dependencies, accessibility, source freshness, analytics, and prototype decisions.
- Quarterly: archive stale claims and pages; review whether the network idea is producing repeat use or should narrow further.
