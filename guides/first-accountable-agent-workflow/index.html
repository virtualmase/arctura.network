Your first accountable agent workflow.

Move from an open-ended instruction to one bounded task, a named reviewer, and a result you can inspect.

By Arctura NetworkPublished 27 September 20262 min read

On this page

Our editorial policy ↗

Choose a small, reversible task

Start with work whose result a person can review before it changes the outside world. Drafting a response from approved material is easier to evaluate than giving an agent permission to manage an entire support queue.

Our illustrative task is a support-response review: read a redacted draft and an approved policy excerpt, identify unsupported claims, and suggest revisions. The agent does not send the message.

Write the standing boundaries

Use an Accountability Card to name the owner, purpose, allowed actions, prohibited actions, and handoff triggers. This is the record that stays with the agent across individual tasks.

For the example, allowed actions include comparing the draft against the supplied policy. Prohibited actions include contacting the customer, changing the account, or obtaining additional private data. Missing policy evidence triggers a handoff.

Write one work order

A Work Order describes the job for this run. Specify the expected output and the exact inputs approved for use. Include excluded inputs so the agent does not infer permission to search private systems.

  • Result: a list of unsupported statements and suggested corrections.
  • Inputs: a redacted draft and a dated policy excerpt.
  • Owner: the team responsible for the workflow.
  • Reviewer: the person who accepts or rejects the result.
  • Stop condition: missing evidence or an instruction outside the task.

Decide the checks before execution

An acceptance check should be observable. “Be helpful” is hard to evaluate. “Every suggested policy statement cites the provided excerpt” gives the reviewer something concrete to inspect.

Include an ordinary case, a case with insufficient evidence, and a request to perform a prohibited action. Record expected behavior before running each case. A refusal can be the correct outcome.

Record what actually happened

Keep intended behavior separate from observation. For each check, record passed, failed, or not run, plus the evidence that supports that status. Do not mark an evaluation successful merely because the JSON is valid.

If a check fails, revise the instruction or control and run it again. Keep the earlier outcome so someone can understand the change. When sharing a result publicly, remove private inputs and identify what was synthetic.

Expand only when the record supports it

Before adding a new tool, data source, or external action, revisit the card and work order. The earlier evidence may no longer cover the changed conditions.

These records are a method for review. They do not enforce permissions by themselves or certify the agent. The responsible operator must implement the boundaries in the actual system.
