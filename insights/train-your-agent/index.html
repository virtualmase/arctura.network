Field Note 001 · Guide

Train your agent by defining the work.

Choose a model for the job. Put it somewhere you can maintain. Give it clear boundaries. Check the result before adding complexity.

By Arctura Network30 August 2026Review by 28 November 2026
On this pageStart with the workChoose a modelChoose where it runsImprove in orderKeep a recordSources

People often say they want to “train an agent.” That phrase can hide several different jobs. Before changing model weights or renting hardware, write down what useful work the agent must do and how you will know it did the work correctly.

01 — Work

Start with a work order.

An agent is not useful because it can talk. It is useful when it can complete a defined task inside clear limits.

Write a short work order before choosing a model:

  • Job: What result should exist when the work is done?
  • Inputs: What information may the agent use?
  • Authority: What may it do without asking?
  • Checks: What must be true before the result is accepted?
  • Record: What should be kept so another person can inspect the work?
Arctura rule

Do not give an agent more authority than the result requires. Responsibility follows authority.

02 — Tool

Choose the smallest capable model.

“Large” and “small” are relative labels, not stable specifications. Model families change quickly. The durable question is whether a model can do the work reliably within your limits for cost, speed, privacy, and maintenance.

Broader model

Use when the work changes often.

Open-ended analysis, unfamiliar inputs, long instructions, and tasks that require several kinds of reasoning may justify a more capable hosted model.

Narrower model

Use when the work repeats.

Classification, extraction, routing, formatting, and other bounded jobs may fit a smaller local or specialized model.

Do not treat size as proof of quality. Test representative examples. Record failures. Choose from measured results, not model reputation.

03 — Place

Put it where the work can be maintained.

The model can run on a machine you control, on rented infrastructure, or behind a managed service. Each choice moves cost and responsibility to a different place.

RouteUseful whenYou maintain
Local machineLearning, private or offline work, bounded modelsThe machine, model files, and uptime
Rented serverThe agent must remain available or needs dedicated hardwareThe operating system, security, capacity, and service
Managed APIYou need a capable model quickly without running itProvider limits, data handling, cost, and fallback behavior
Check capacity before renting. Model format, quantization, context length, concurrency, RAM, and GPU memory all affect whether a workload fits. Test the actual workload before committing to a long-running server.

04 — Improvement

Improve the agent in the least expensive order.

Training model weights is only one way to improve a system. Climb only as high as the evidence requires.

  1. 1

    Instructions

    State the job, boundaries, examples, and acceptance checks. No model weights change.

  2. 2

    Retrieval

    Give the agent approved documents or current data when it works. Use this when the problem is missing knowledge.

  3. 3

    Tools and workflow

    Let the agent call a narrow tool or follow a fixed sequence. Use this when the problem is action, not language.

  4. 4

    Fine-tuning

    Adjust model weights using a reviewed dataset. Use this when repeated evaluations show a stable behavior gap that earlier steps do not fix.

  5. 5

    Pretraining

    Build a base model from raw data. This is research infrastructure, not a normal first-agent task.

Arctura rule

Keep what works. Fix what does not. Complexity must earn its place.

05 — Proof

Check the work and keep the record.

A good demonstration is not an operating record. Build a small evaluation set from real examples, including cases the agent should refuse or send to a person.

For each change, record:

  • the work order and its version;
  • the model and serving configuration;
  • the examples used for evaluation;
  • the acceptance checks and measured results;
  • known failures and who reviews them;
  • the reason for keeping or reversing the change.

This is what turns experimentation into stewardship. No one should have to take your word for it.

06 — Decision

A first build that is easy to reverse.

  1. Choose one bounded task with a result you can check.
  2. Try a managed model or a small local model before buying infrastructure.
  3. Write ten to thirty representative checks, including failure cases.
  4. Add retrieval only if the agent lacks approved facts.
  5. Add tools only when the work requires action.
  6. Consider fine-tuning only after the record shows a repeated gap.
  7. Review access, cost, failures, and maintenance before making it permanent.

The aim is not to build the most advanced agent. The aim is to build one whose work holds up.
