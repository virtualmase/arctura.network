Briefing / Authority

A tool connection is not permission to act.

Before connecting an agent to another system, define who authorizes the work, which actions are allowed, and where that authority ends.

By Arctura NetworkPublished 27 September 20262 min read

Our editorial policy ↗

The source signal

The Model Context Protocol security guidance describes risks around delegated access, including confused deputy attacks and token passthrough. Its consent guidance calls for explicit approval tied to the requesting client. A working connection alone does not establish that a particular action is appropriate.

Source: MCP security best practices, versioned guidance ↗

What this means in practice

Arctura’s practical interpretation: separate the technical ability to call a tool from the owner’s permission to perform the task. An agent that can read a support ticket should not inherit permission to send a reply, issue a refund, or export the customer history.

The useful record is specific. Name the system, action, permitted inputs, time window, and responsible owner. “Help with support” leaves too much for the system to infer.

Make the boundary testable

For a support-review agent, a bounded instruction might allow reading an approved, redacted ticket and drafting a response. Sending the response remains a person’s decision. Record the distinction before connecting the tool.

  • Name one allowed read and one prohibited write.
  • Try a request outside the task and record whether the agent refuses or asks for authorization.
  • Define what happens when access expires or the owner withdraws permission.
  • Require a new approval when the action or destination changes.

What this does not establish

An accountability card records the intended boundary. The actual system still needs access controls and tests that enforce it. This briefing is a review pattern, not a security assessment of an MCP implementation.
